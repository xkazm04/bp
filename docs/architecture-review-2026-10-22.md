## 3. Options A and B as repo diffs

Both options in R1 put the headers at `apps/vr/Source/BpLink/Public/Schema/`. That is the directory `ed94a65`'s
spelling already names, so neither option re-spells BpLink's includes. The line counts below come from reading the
code. They are not from a written patch.

### Option A: the generator writes both locations

| Change | Where |
|---|---|
| Two constants for the new paths, two more entries in `outputs` | `generate.mjs:46-47`, `:506` |
| Stale comparison and stale controls for the new copies | **no new code**: the loop at `:547-554` and the controls at `:764-775` iterate `outputs`, so each copy is compared with a fresh generation and gets its own "one line mutated / one line deleted" controls |
| Two new committed files | `apps/vr/Source/BpLink/Public/Schema/BpSchema.h`, `BpSchemaFixups.h` |
| `PublicIncludePaths` entry | drop `BpLink.Build.cs:19-22` (see below). If dropped, `check-bplink.mjs:417-419` fail as written, because they require a `Path.Combine` |
| `check:bplink` include checks | `check-bplink.mjs:413-427`: resolve `Schema/X` under `MOD/Public/`, not by stripping `Schema/` (about ten lines) |
| `check:gate-helpers` | unchanged if `includeParts` stays exported |
| `ue-standin/check.cpp` | unchanged: the packages copy still exists |

- **Parity control.** Each copy must equal a fresh generation. That already implies the two copies are equal, so a
  separate copy-to-copy step adds a clearer message and no new coverage. The comparison runs after `norm()`
  (`generate.mjs:491`, CRLF to LF). That makes it LF-normalised text parity, not the "byte" parity R1 names.
  `core.autocrlf` is `true` here (Ran), and machine.md:68 records CRLF working copies. (Inferred: harmless, because
  both copies get the same checkout treatment. The wording in R1 should say "text".)
- **Failure when someone edits one copy.** `check:schema` prints `FAIL  <that path> is stale: run npm run
  schema:generate (first difference at line N ...)` (format at `:553`) and exits 1. CLAUDE.md makes `npm run check`
  green a push precondition, so a hand-patched copy made to get UBT through on Wolf is refused at the push. An edit made
  identically to both copies fails the same way.
- **Why drop the Build.cs entry under A.** If it stays, `"BpSchema.h"` reaches the packages copy and
  `"Schema/BpSchema.h"` reaches the module copy. These are two different files with the same USTRUCTs. A translation
  unit that reaches both is no longer a `#pragma once` question; it is two definitions of every struct. (Inferred, not
  measured.)
- **Ongoing cost.** Committed generated files go from 3 to 5 per schema change. Every UE diff shows up twice in review.
  The packages copy keeps two readers: `check:schema` itself and the ungated clang smoke.

## 4. Option C after `ed94a65`

R1's row (wolf-plan:589) and its ask (`:639-640`) are conditional: "If UHT will not process the junctioned
`BpSchema.h`". On Lynx, UHT did process it (machine.md:101-105, and readings 3, 7 and 8). The condition R1 was written
for has not occurred on Lynx. On Wolf it has not been tried.

What `ed94a65` changed, read against the readings:

- **It did not create the dependency on something under `Public/`.** Reading 1, at `4a3353a`, with the bare spelling
  and no junction, already failed: `BpSchema.h(13,1): fatal error C1083: Cannot open include file:
  'BpSchema.generated.h'` (machine.md:89). UHT only reads headers under the module's own directory (machine.md:84-86).
  So the repo has never built BpLink on Lynx without a `Public/Schema` entry.
- **It moved the failure and named the location.** Without the junction the error is now at `BpLink.h(7,1)` on
  `'Schema/BpSchema.h'` (reading 9). The path `Public/Schema/` is written into BpLink's own source and pinned by
  `check-bplink.mjs:428-436`.
- **It made the `PublicIncludePaths` entry unnecessary for BpLink's own includes (Inferred).** With the junction,
  every BpSchema path in the compiled TUs is under `public\schema\` and none is under `packages\schema`
  (machine.md:217-219, :236-237). `BpSchemaFixups.h:19`'s bare include resolves beside itself (machine.md:209-212). No
  reading has built with the entry removed.

So "C changes nothing" (wolf-plan:648-649) is **still true as a diff**: C commits nothing. It is **no longer true as
"nothing is decided"**. With C, the junction is the mechanism of record. That arrangement was never written as a
decision, and E1's three follow-ups are missing from the tree: the ignore line (§2), the link script (§2), and
repointing or dropping the Build.cs entry. `WP3.1.md:68-69` records that last one as deferred to R1. W3.1-4's expected
error text is also stale (§2, step 1).

**The revert, examined.** One candidate third option is to put the spelling back to `"BpSchema.h"` so the tree builds
with no junction at all. Reading 1 says it would not: the bare spelling without the junction fails one header deeper,
at `BpSchema.generated.h`. With a junction present, the revert brings back reading 5b's `C1189` whenever a unity file
merges `BpSchema.gen.cpp` and `BpLink.cpp`. A default build does not merge them while the module has fewer than 32
source files (machine.md:203-205), so that cost stays hidden until the module grows or someone forces unity. The revert
does not give a build that needs no junction, and it brings back a defect that has already been measured.

**The honest third option, as I read it, is "C′: the junction, finished".** It keeps one file on disk. It is the only
arrangement measured to exit 0, for both targets. It would add:

- the `.gitignore` line;
- `apps/vr/tools/link-schema.ps1` with an absolute target;
- W3.1-4 reworded to the `Schema/BpSchema.h` error;
- the Build.cs entry repointed at `Public/Schema` or dropped;
- a `check:bplink` line that names the junction as a precondition, instead of resolving `Schema/` through the
  packages directory as if the junction were there.

Its costs stay: one manual, Windows-only step per checkout per host; a fresh clone does not build; no CI step can
create the junction, so CI never covers it. C as written today is C′ without the five additions.

**Which way the evidence leans (my reading, not a recommendation to adopt).** The structural evidence favours a
committed directory at `Public/Schema/` over the junction. A clone would build. Git would hold the bytes UBT compiles.
The four by-hand steps in §2 would go away. Between A and B, I lean narrowly to **A**. Its staleness control costs no
new code, because `outputs` already drives the check and its controls. It also leaves `packages/schema`'s published
location, the clang smoke and the `includeParts` tests alone.

The counter-cases, stated as strongly as I can:

- **For B.** A keeps two copies of the same file. Every UE schema diff shows up twice. The packages copy has no
  compiled reader. B is the smaller tree to live with, and its extra check edits are one-time.
- **For C′.** It is the only option with measured exit-0 builds behind it. It keeps a single file and keeps
  `packages/schema` ignorant of `apps/vr`. A and B are inferred to build and have never been through UBT. Choosing
  either on Lynx evidence alone swaps a measured mechanism for an unmeasured one.

## 5. Other problems at the same boundary that cost more later

### 5.1 The include-path entry is a second, public route to the header

`BpLink.Build.cs:22` adds `packages/schema/generated/ue` to **Public**IncludePaths. wolf-plan E3 (`:536-538`) says
any other module that includes the headers must depend on `BpLink`. Inferred, from UBT's public/private split and not
measured: such a module inherits that path, so `#include "BpSchema.h"` resolves there. A TU that also reaches
`Schema/BpSchema.h` then hits reading 4's `C1189` (machine.md:181-190). The one-spelling rule only reads `BpLink.h`
and `BpLink.cpp` (`check-bplink.mjs:423`), so the game module `bp`, or any later module, is not covered.

- Cost now: four lines in the Build.cs, a decision E1 already proposed.
- Cost later: a C1189 in another module's build on Wolf.
- Under A with the entry kept, it gets worse: two distinct files, not two paths to one file.

### 5.2 `check:bplink` treats the junction as a fact

`check-bplink.mjs:420` says it in a comment: "`Schema/` is WP3.1's junction ... so `Schema/X` is read there as X". Line
`:425` strips `Schema/` and looks in the `PublicIncludePaths` directory. The result (Ran) is `ok build: every Bp* header
BpLink includes is in that directory (Schema/BpSchema.h, Schema/BpSchemaFixups.h)`. That passes on this tree, where
`Public/Schema` does not exist and the UE build fails at that include (reading 9).

- The only gate that speaks to BpLink's includes is green on a tree that cannot build from a clone, on CI as well as
  locally.
- Cost now: one check, rewritten for whichever layout is chosen (§3, §4).
- Cost later: a green gate and a red Wolf build, with the gate's line telling the Wolf session the include is fine.

### 5.3 No gate compiles the generated headers, and the one compiler-based smoke is pinned to the old layout

`generate.mjs:636-637`: "No gate here can run a C++ compiler". The clang smoke lives as a comment command,
`ue-standin/check.cpp:2`. It uses `-Ipackages/schema/generated/ue` and the bare `"BpSchemaFixups.h"`. Its last
recorded run covered 3 of the 6 roots (`apps/vr/README.md:64-67`). `check:schema` asserts only that the file *names*
all six (`:640-660`). The only compiles of the headers since then are machine.md's UBT readings, which instantiate
what BpLink uses.

- Under B, the smoke's path silently goes stale.
- Under any option, a FixUp body for a root BpLink does not read has not been through a compiler.
- Lynx now has MSVC (machine.md:25), so this gap is no longer forced by the host. Closing it is a gate design question
  (which compiler, against stand-ins or UE). That question is for the owner, and this review does not decide it.
- Cost now: one ungated command. Cost later: a generator change that breaks an unread root is found in a Wolf build.
