# Plumbline scenario - lessons for bp and the skills

One entry per finding: what happened, the bp or skill change it asks for, and its status. A finding seen twice is promoted
into the spark overlay's `## Gates` or `## Repo law` (that is the method's own rule).

| # | Date | Phase | Finding | Change asked for | Status |
|---|---|---|---|---|---|
| L1 | 2026-11-17 | P0 | A Windows repo that hashes raw files (a lock, a vendored runtime) drifts under `core.autocrlf`; bp's repo law covers CRLF in regexes, not in hashes. Plumbline needed `.gitattributes eol=lf` from its second commit. | `/adopt-bp` and the spark overlay: when a product hashes raw files, check for `.gitattributes` first. | proposed |
| L2 | 2026-11-17 | brainstorm | A contest or market target needs an evidence scout of the LIVE entrants before the brainstorm. The brainstorm's first pick was already built twice (Agent Atlas, Agent Customs), found only after four waves because the spark's scouts read code, not ecosystems. It cost two re-asks of the owner. | `spark` Phase 2: when the target is a contest, market or standard, scout the live entrants or incumbents (read their source, not their blurb) before wave 1, and put what they already cover into the question options. | proposed (first sighting) |
| L3 | 2026-11-17 | brainstorm | A fetched digest of a spec said "no validator exists"; a competitor's own page showed one did. A subagent's absence claim is a hypothesis. | `spark` scouts: an absence claim ("no X exists") is checked against one live counter-example search before it shapes a question. | proposed (first sighting) |
| L4 | 2026-11-17 | P1-P2 | Two parallel builders were green alone; the integration broke one test because WP1 asserted a stub's placeholder output ("not implemented") for commands WP2 owned. bp's overlay already says to run the full check where packages meet; it does not say a builder must not pin a sibling's stub behaviour. | spark builder briefs: "never assert the placeholder behaviour of a stub another package owns"; the Director's first integration run is where it shows. | seen once; logged |
| L5 | 2026-11-17 | P2 | Upstream moved on day one: the vendored runtime's source (nsdeploy) is already ahead of the commit the reference copies (53a787c vs 4e4cb36), measured by the new watch. A product built on a fast-moving draft spec has drift as a standing input, which is exactly what bp's scans and stand-ups should surface without being asked. | bp: the Morning Watch could read a product's own drift report (plumbline watch --json) as a card source once the product is adopted. | idea, for the stand-up phase |
| L6 | 2026-11-17 | P3 adopt | /adopt-bp refused six honest quality-lens coverage rows: judgement.md asks for a row per technique touching ANY judged lens, but `judge` accepted rows only for development, security and design. | adopt-bp 1.6.1 (ai-registry 414f09f76, 48b21085b): rows accepted and stored for every manifest-judged lens; standardsPct derived only where the lens manifest declares it (quality, business, operations 1.1.0 do not). | fixed |
| L7 | 2026-11-17 | P3 adopt | A value a faulty run wrote into the store stays in the map: the store is append-only and the map keeps each key's latest value, so nothing newer replaces or retracts it (three quality standardsPct warnings remain on Plumbline from the first 1.6.1 attempt). | lens-scan: a retraction row, or a measure run that can state "this key no longer applies". | open |
| L8 | 2026-11-17 | P3 stand-up | A product's next.steps could never show its own decisions: `nextStepsRead(product)` built the cross-product deck (top 3 decisions) and then filtered it, so Plumbline's three tier-1 decisions sat behind pof's 51. Also, a facet judged `applicable: false` (design on a CLI feature) was counted as an unmeasured gap. | bp: `morningDeck(..., product)` scopes the deck to the product; `gaps()` skips not-applicable facets. Smoke on the real stores: Plumbline's next.steps now lead with its three tier-1 decisions; design gaps on its CLI features 0. | fixed |
| L9 | 2026-11-17 | P3 | `scripts/kill-port.mjs` said "nothing listens" for a server still answering 200: on this Windows build netstat reported the live listener as CLOSED, then FIN_WAIT_1, and twice not at all, all while `npm run check` loaded the machine. 20 of 20 samples read LISTENING when quiet. | kill-port matches a listener by its wildcard foreign address, not the State column. Partial: covers the misread states; the two outright misses are unexplained. Retry, and confirm by PID with netstat when it says nothing listens. | partly fixed |
